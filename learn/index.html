01

A policy is a document

meta · evaluators · eval_expression

Every Tirith policy has the same three parts. meta names the provider that will read your input. evaluators is the list of checks. eval_expression says how their results combine into one verdict. Nothing here is a program: it is a description of what to look for.

The provider decides what kind of document you are allowed to feed in. stackguardian/json reads any JSON or YAML by key path, which is why it is the one this playground implements.

Try itChange the region to us-east-1 and watch the verdict and the exit code move.

02

One check, many values

wildcards · every value must pass

A * in the key path iterates a list or a dict, and the provider returns one value per match. The condition then runs against each value independently, and the evaluator passes only if every one passes. Three services, three result lines, one verdict.

This is the rule that surprises people most often. A wildcard check is not "most of them are fine" — a single value that fails, fails the evaluator.

Try itDrop the value to 1. One failing line is the difference between exit 3 and exit 0.

03

Combining checks

&& · || · grouping

Give each check an id, then join them in eval_expression. a && b needs both, a || b needs either, and parentheses group. The expression is the one part of a policy you cannot derive from the checks themselves.

Because the expression names ids, it is also where a policy documents its own intent. Read the expression first when you are trying to understand someone else's rule.

Try itSwap && for ||. One passing check is now enough to carry the whole policy.

04

The detector that lies

! · and the trap under it

You want "no image on a floating tag". The tempting way: write a check that finds :latest, then negate it with !. The output below says PASSED — and it is wrong. Look at admin in the document. It is on :latest, and this policy just waved it through.

Because the condition runs against each value and the evaluator passes only if EVERY value passes, uses_latest can only pass when all three images are :latest. One normal image makes it false, and !false is true. The ! is not the bug — the check underneath it is asking the wrong question.

Try itFix it: change the condition to NotContains with value ":latest", and change the expression to plain no_floating_tag. Now each image is judged on its own, admin fails, and the exit code is 3 — which is what you wanted all along.

policy.json
input.json
showing the current policy
stdoutfinal_result true · exit 0
$ tirith --fail-on-error -policy-path policy.json -input-path input.jsonCheck: uses_latest  FAILED    1. FAILED: `"ghcr.io/acme/api:1.4.2"` does not match regex pattern `":latest$"`    2. FAILED: `"ghcr.io/acme/worker:0.9.0"` does not match regex pattern `":latest$"`    3. PASSED: `"ghcr.io/acme/admin:latest"` matches regex pattern `":latest$"` Passed: 0 Failed: 1 Skipped: 0 Final expression used:-> !uses_latest$ echo $?0
05

When the path is not there

error_tolerance · a skip is not a pass

If a key path matches nothing, that is an error, not a false. By default the check fails. Raise error_tolerance to 2 and the provider error is *skipped* instead — and a policy where every check skipped evaluated nothing at all, so it reports final_result: null and exits 1, not 0.

A skip is not a pass. This is the distinction that separates a gate that is working from one that is quietly matching nothing.

Try itSet error_tolerance to 0. The same missing path now fails the check and the exit code changes from 1 to 3 — different problems, different codes.

policy.json
input.json
showing the current policy

The whole thing

a policy you would actually commit

Four checks, a grouped expression, and a description on each so a failing run explains itself. This is the shape of a file you would put under .tirith/policies and point a pipeline at.

Note the tag check is the corrected form from step 04, not the ! version. From here the only things that change are the provider and the key paths. The conditions, the expression language and the exit codes are the same for a terraform plan, a Kubernetes manifest or an Infracost breakdown.

Try itFix the document instead of the policy: give the worker 2 replicas and pin admin to a real tag, and the whole thing goes green.
